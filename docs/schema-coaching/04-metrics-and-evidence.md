# 04 — Metrics & Evidence (every measured/numeric field, with source)

Rule (kickoff Stage 4): no metric columns on vibes. Each row: why it exists, scale/unit, source of
truth, and what happens when the number is missing or wrong. Money is integer pence (R05).

| Field | Table | Why it exists (product reason) | Scale / unit | Source (evidence) | Missing / wrong behaviour |
|---|---|---|---|---|---|
| `price_from_pence` | `treatments` | The "From £35 per session" promise is the client's trust hook (W04); the app must show the *published* figure, never a float or a guess | integer pence, 3500–12000 for the 8 core site prices | W04 (verified 22 & 26 Oct 2026); R05 | NULL ⇒ `pricing_model = PRICE_ON_CONSULTATION`, card reads "Price on consultation" (S04). A wrong value = a broken promise on launch day — Engine A-01 pins the 8 values. |
| `price_from_pence_snapshot` | `booking_requests` | A request must forever display the price the client saw at submit time, immune to later edits and GDPR pseudonymisation | integer pence | R05 (snapshot rule); W03 request flow | Server-computed (trigger) — a client-supplied value would be a forgery. Engine P-03 asserts 3500 for hair removal. |
| `typical_sessions_min / max` | `treatments` | Sets expectation ("six to eight sessions") — the site's main FAQ answer; drives S04 copy only, never scheduling logic | smallint count | W04/FAQ per treatment (hair 6–8, tattoo 6–10, rejuvenation 3–6, tightening 3–5, pigmentation 1–3, veins 1–2, acne 4–6, peel 1) | NULL ⇒ UI shows "Discussed at consultation" (S04, never invent). |
| `duration_minutes` | `treatments`, `appointments` | Appointment sizing for the staff queue and "lunch break" FAQ answer | minutes (integer) | `/faqs/` Practical (verified 26 Oct): peel 30; consultation 20–30; per-area times are ranges in copy, not per-treatment numbers | NULL ⇒ staff set it at confirm (S12). Only published values seeded — area-variant times stay prose until Q13. |
| `min_gap_days` | `treatments` | Safety spacing between sessions of the same treatment | integer days; currently only 42 | FAQ "spaced six weeks apart" for tattoo removal (W04/FAQ, verified) | NULL (all other treatments) ⇒ no warning possible; owner Q5 (intervals by treatment/area) unblocks. Enforced as **warn-to-audit only** (DA-05/E1). |
| `sessions_count = 6`, `discount_percent = 20` | `course_packages` | The published course offer; catalogue data the app may display and staff may record | integer count / integer % | `/faqs/` verbatim: "course packages of six sessions at 20 per cent off most treatments" (verified 26 Oct) | Homepage copy "six or eight" flagged to owner (04-schema §1.2). Absolute package `price_pence` stays NULL — not published ⇒ never derived in DB (R05). |
| `staff_seat_max = 2` | `clinic_settings` | M01's "owner, and 2 people to control it" as an auditable setting, not folklore | integer seats | M01 (STATED — Q01/owner Q1 confirms) | Trigger rejects the 3rd active staff grant (Engine P-11). Changing the number is a settings edit, not a migration. |
| `reminder_lead = '24h'` | `clinic_settings` | M01 "check reminders"; server needs a deterministic scheduling offset | duration string parsed to interval | D07, S07 default; owner Q6 pending (DA-08) | Only confirmed appointments get rows; reschedule cancels/re-creates (P-07). |
| `preferred_time_band` | `booking_requests` | The site itself only asks day + time preference — a slot count would be fictitious availability | 3-value enum `MORNING\|AFTERNOON\|EVENING` | W03 (1-working-day callback); Q04 open | NULL allowed (client picks day only). |
| `fitzpatrick_type` (DORMANT) | `clinical.skin_assessments` | If/when in-app skin data is opted in: the site's safety story is Fitzpatrick-calibrated settings | smallint 1–6 (I–VI) | `/faqs/` names Fitzpatrick I–VI explicitly; site text W06 | **Not collected in v1** (D05/R04/DA-10). | `expires_at` | `client_courses` | Course validity, if the clinic ever defines one | timestamptz NULL | DA-16 — nothing published about expiry/rollover | NULL in demo = "no expiry rule on file" (owner Q11), not "never expires". Usage is computed, never stored. |
| `attempts` | `reminders` | Dispatch reliability telemetry for server push | smallint, starts 0 | D07 (Edge Function owns) | Bounded retry only; no user-facing meaning. |
| `phone_verified_at` (gate for uniqueness) | `client_profiles` | M01 "email and number" — uniqueness where it matters (verified numbers) without punishing unverified sign-ups | timestamptz NULL | S01; DA-12; owner Q13 | Unverified duplicates allowed + flagged to staff; verified duplicates rejected by partial unique index (P-02). |
